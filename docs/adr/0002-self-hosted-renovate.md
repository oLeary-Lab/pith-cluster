# 0002. Self-hosted Renovate as an in-cluster CronJob

Status: accepted (staging)
Date: 2026-11-07
Amended: 2026-11-08 — the credential model (§7) is superseded by ADR-0004.

## Context

The repo pins dependencies in three forms: HelmRelease chart versions in
`<area>/base/controllers` and `<area>/staging/controllers`, container images in
manifests (`apps/base/linkding/deployment.yaml`,
`clusters/staging/flux-system/gotk-components.yaml`), and developer tool
versions in `mise.toml` + `mise.lock`. Nothing scans for updates, so every bump
is manual. The recent eMudhra CA-trust and OpenSSH issues (see the
Flux/kube-prometheus-stack/edge commits) showed the cost: a trust-revocation fix
had to be hand-carried across several controllers.

The repo already states the policy the scanner must implement: a 14-day
release-age floor (`mise.toml` `minimum_release_age = "14d"`), with security
exceptions taken deliberately and recorded in the commit/ADR (as the Flux
v2.10.0 bump did). Existing conventions the component must fit: Flux
HelmReleases pin chart versions exactly; workload images are hand-pinned by
digest; secrets are SOPS/age encrypted; tiers are split `base`/`<env>` and
`controllers`/`configs`; Flux decryption is enabled per-Kustomization.

Tier semantics are set by precedent rather than defined in ADR-0001. The
`controllers` tier holds Helm-released cluster components that other things
depend on (`infra/.../controllers/traefik`,
`monitoring/.../controllers/kube-prometheus-stack`). The `configs` tier holds
raw workloads and their environment configuration, including a plain workload
with its own Secret (`infra/base/configs/cloudflared/deployment.yaml` +
`infra/staging/configs/cloudflared/tunnel-credentials.yaml`). Renovate is a raw
`CronJob`, which matches the `configs` shape.

The requirement is therefore: scan for dependency updates, propose them as PRs
against `main`, hold them to the 14-day floor, surface real security fixes
promptly, keep the scanner's own image cryptographically pinned, and stay
declared in this repo.

## Decision

1. **Run Renovate self-hosted in-cluster as a plain Kubernetes `CronJob`** (raw
   manifest), not a Helm chart, not an operator, not a hosted service. It lives
   at `infra/base/configs/renovate` with the staging overlay in
   `infra/staging/configs/renovate`, wired into
   `infra/staging/configs/kustomization.yaml`. It is a workload, so it belongs
   in the same tier as `cloudflared`, not with the Helm-released controllers.
2. **Pin the job image by tag *and* digest, from Docker Hub**:
   `renovate/renovate:44.181.4@sha256:e2440463a0fff07e43875643324f8b57f6c3a9a8365332b7183989514f81e9ee`.
   `44.181.4` (published 2026-10-24) is the newest release clearing the 14-day
   floor. Docker Hub is chosen over GHCR deliberately: Renovate's Docker
   datasource only reads release timestamps from Docker Hub (`tag_last_pushed`),
   so a GHCR reference could not be age-gated by `minimumReleaseAge`. Both
   registries serve the same digest. Renovate maintains this reference itself
   via the `kubernetes` manager.
3. **Express the policy in a repo-level `renovate.json`**: `extends
   config:recommended`, `minimumReleaseAge: "14d"`, `osvVulnerabilityAlerts:
   true`, `pinDigests: true`, and broadened file patterns for both the
   `kubernetes` and `flux` managers. Two manager defaults make this mandatory:
   the `kubernetes` manager ships with *no* file patterns (it matches nothing
   otherwise), and the `flux` manager ships matching only
   `**/gotk-components.y(a)ml`, so it must be widened before it will touch our
   HelmReleases. The generated `clusters/staging/flux-system/gotk-components.yaml`
   is excluded via `ignorePaths`, since it is regenerated by `scripts/bootstrap.sh`.
4. **Pin digests everywhere, in a single canonical form.** Workload images are
   already hand-pinned; `pinDigests` formalises it. The canonical form is
   `image:tag@sha256:…` (tag retained for version context and so Renovate can
   reason about updates), replacing the digest-only `image@sha256` form. A
   `packageRules` entry scopes `minimumReleaseAge: null` to `pinDigest` updates
   so pinning is not blocked by the age gate.
5. **Awareness and adoption are separate surfaces.** The Dependency Dashboard
   (enabled by `config:recommended`) is where pending updates, including those
   held by `minimumReleaseAge`, are reviewed. `internalChecksFilter` is left at
   its default `strict`, so no branch or PR is created until the floor passes.
   The Dashboard, not early PRs, keeps us abreast.
6. **Security exceptions are automatic, not hand-carried.** OSV-driven security
   updates bypass `minimumReleaseAge` and are raised as soon as detected; the
   exception is then recorded in the merge commit/ADR as usual.
7. **Credentials** *(superseded by ADR-0004)* are a fine-grained GitHub PAT
   scoped to only `oLeary-Lab/pith-cluster`, stored SOPS-encrypted as the Secret
   `renovate-dotenv` alongside the component. Required token permissions:
   Contents, Issues, Pull requests, Commit statuses = read+write;
   **Dependabot alerts** and Metadata = read-only. `Dependabot alerts: read` is
   kept despite `osvVulnerabilityAlerts`: OSV is an additional source, not a
   replacement. The GitHub platform path
   (`lib/modules/platform/github/index.ts` `getVulnerabilityAlerts()` →
   `/repos/{owner}/{repo}/dependabot/alerts`) is gated separately from the OSV
   path (`lib/workers/repository/process/extract-update.ts`, gated only on
   `osvVulnerabilityAlerts`), so dropping the scope would disable GitHub-native
   vulnerability PRs. The credential is dedicated to Renovate and is never
   shared with any developer or automation token.
8. **The Secret is decrypted by the tier that already decrypts.** It lives in
   `infra/staging/configs/renovate/`, which the existing `infra-configs`
   Kustomization already covers with its SOPS provider. No decryption is added
   to `infra-controllers`, so that tier's trust boundary is unchanged.
9. **Runs are observed through the existing monitoring stack.** A
   `PrometheusRule` in `monitoring/staging/configs/renovate` alerts on
   `RenovateStale` (no successful CronJob run in over 2 days), a
   `RenovateNeverRan` companion (`absent()` with a 48h grace window, because
   `kube_cronjob_status_last_successful_time` does not exist until the first
   success), and `RenovateJobFailed`, using kube-state-metrics' CronJob/Job
   metrics. No new component is introduced.
10. **mise toolchain versions are not managed by Renovate.** `mise.toml` is
    `locked = true` and `mise.lock` pins exact versions and checksums;
    refreshing that lock (`mise lock`) runs repo-defined scripts and is treated
    by Renovate as an unsafe execution, so Renovate cannot keep the two in sync.
    Tool versions stay on mise's own `minimum_release_age` policy. This is a
    dev-environment concern only; it has no bearing on cluster manifests.
11. **Harden the job**: `concurrencyPolicy: Forbid`, `restartPolicy: Never`,
    `startingDeadlineSeconds`, `backoffLimit`, `activeDeadlineSeconds`,
    `ttlSecondsAfterFinished`, bounded job history, the ServiceAccount token not
    mounted (`automountServiceAccountToken: false` — Renovate never calls the
    Kubernetes API), a non-root/read-only-rootfs least-privilege
    `securityContext` (uid/gid `12021`, matching the image), resource
    requests+limits, and a size-limited `emptyDir` cache at `/tmp/renovate`.

## Consequences

1. Renovate opens PRs against `main`; Flux reconciles whatever is merged. The
   branch-protection ruleset on `main` bounds the blast radius of a compromised
   token to PR creation, not cluster change — **while `main` is protected with
   no admin bypass**. A `Contents: write` PAT can still push to *unprotected*
   branches, and once CI exists a pushed branch can run workflows with repo
   secrets; today there is no `.github/` and no CI, so that path is inert.
2. Dependency updates now arrive as PRs under a uniform 14-day floor; CVE fixes
   arrive immediately. The exception path stops being manual.
3. The cluster now holds a repo-write credential. It must stay SOPS-encrypted,
   scoped to the single repo, and be rotated on its PAT expiry.
4. The Renovate image is itself a pinned supply-chain input, updated under the
   same floor by Renovate itself.
5. The Dependency Dashboard issue becomes the operational surface for reviewing
   pending updates, and the `RenovateStale`/`RenovateNeverRan`/`RenovateJobFailed`
   alerts are the signal that scanning has stopped.
6. Placing the component in `configs` keeps the Secret in the one tier that
   already decrypts, so no tier gains a decryption capability it did not have.
7. `pinDigests` produces a new stream of grouped "Docker digests" PRs and a
   one-time normalisation of existing references.

## Rejected

1. **The `renovatebot/helm-charts` chart.** Its `cronjob.yaml` interpolates the
   image as `repo:tag` with no digest field, so it structurally forfeits the
   SHA pin. Its value over a hand-written CronJob (~40 lines plus the same
   Secret/ConfigMap wiring) is not worth that.
2. **`renovate-operator` (CRD + UI + webhooks).** A controller, CRDs and a UI to
   run one job for one repo. Revisit if this becomes multi-repo with webhook
   triggers.
3. **A GitHub Action or the hosted app.** Moves the scan out of the cluster;
   the point is to exercise the cluster and keep everything declared in-repo.
4. **Opening PRs before the 14-day floor** (`internalChecksFilter: "flexible"`).
   Produces stale queues and alert fatigue, which is the failure mode that makes
   a real security PR get missed. The Dashboard gives awareness without
   adoption.
5. **Scoped `dependencyDashboardApproval`.** At this scale it adds a second
   manual step (tick on the Dashboard, then review the PR that appears) with no
   boundary beyond the age gate plus branch protection, which already prevent
   unaged adoption and unintended merges. The Dashboard lists pending items
   either way. Reintroduce — scoped to majors or the `flux`/`helmv3` managers —
   only if PR volume grows enough to need a creation gate.
6. **Placing the component in the `controllers` tier.** It is a raw workload,
   not a Helm-released controller, and the Secret would have forced SOPS
   decryption onto `infra-controllers` — a capability it does not otherwise
   need. `configs` matches the `cloudflared` precedent and reuses the existing
   decryption.
7. **Moving only the credential to `configs` while leaving the workload in
   `controllers`.** It avoids the decryption expansion but splits the
   component's files across two tiers for no functional gain; moving the whole
   component is simpler to navigate.

## Deferred

1. **A GitHub App instead of a PAT.** *(Adopted — see ADR-0004.)* Stronger in
   principle (short-lived, org-owned tokens), but Renovate's self-hosted CLI has
   no native App auth: it
   requires a pre-minted installation token that expires hourly, regenerated by
   a sidecar/init container. That adds another pinned image and key management
   for a single-repo homelab. Revisit if the cluster grows.
2. **Age-gating GHCR images.** Renovate's Docker datasource reads release
   timestamps only from Docker Hub, so GHCR-hosted images cannot be held to
   `minimumReleaseAge`. Currently only affects the excluded Flux system
   manifests; revisit if a GHCR workload image needs the floor.
3. **`RENOVATE_TOKEN` rotation.** *(Resolved — see ADR-0004.)* The PAT has a
   fixed expiry; there is no automated renewal or expiry alert yet.
4. **CI.** There is no `.github/` and no manifest-validation gate, so nothing
   checks the manifests Renovate's own PRs will touch. A `kubectl kustomize` +
   schema-validation job is the highest-value follow-up, but it is a separate
   change.
